# Waffle Pi 바퀴 기하와 오도메트리 보정

> 보존용 분석 기록입니다. 이 문서의 옛 벽 추종 실행 명령은 현재 실행 절차가 아닙니다. 현재 프로필은 [0.10m/s 실행 안내](../guides/README_House_010_초기화실행.md), 유지된 측정 도구는 [wheel_geometry_audit.py](../../wheel_geometry_audit.py)를 참고하세요.

## 확인 순서

이번 `라이다 또는 오도메트리 수신 중단` 정지는 마지막 센서 콜백 이후 1초 이상 수신 공백이 관측됐다는 의미입니다. 축간거리 오차를 검출한 메시지가 아닙니다. `wall_follow_scan.py`는 이제 `/scan`과 `/odom` 각각의 수신 공백을 출력하도록 변경했습니다. 시간 제한 없는 매핑·복귀 설정은 유지합니다.

`map -> odom`이 이동하는 것은 SLAM 보정일 수 있습니다. 출발 위치에서 멀어졌다는 이유만으로 바퀴축 오차로 확정할 수는 없습니다. 이번 단계에서는 바퀴 치수와 오도메트리 생성 경로를 실제 설치 모델에서 확인합니다.

## 공식 모델에서 계산되는 값

| 항목 | 값 |
|---|---:|
| 좌우 바퀴 중심 y | +0.144m, -0.144m |
| 형상 기준 중심 거리 | 0.288m |
| 차동구동 설정 중심 거리 | 0.287m |
| 좌우 바퀴 반경 | 0.033m |
| 설정 바퀴 지름 | 0.066m |

중심 거리 차이는 약 0.35%입니다. 설치 모델이 같은지 확인해야 하며, 이 작은 기하 차이만으로 현재의 큰 지도 왜곡 원인을 설명했다고 볼 수 없습니다.

공식 Gazebo 차동구동 플러그인의 `odometry_source` 기본값은 1(WORLD)입니다. 0은 ENCODER입니다. WORLD 모드에서는 시뮬레이터 위치가 오도메트리 기준이므로 바퀴축 값을 변경해 엔코더 누적 오차를 직접 고치는 구조가 아닙니다. 치수는 명령 속도와 실제 구동의 관계에는 영향을 줍니다. ENCODER 모드로 바꾸는 것을 지도 왜곡 해결책으로 간주하지 않습니다.

## 1. 설치 모델 비교

Windows의 `wheel_geometry_audit.py` 하나를 Ubuntu의 `~/ros2_practice_ws/`에 복사합니다. 빌드는 필요하지 않습니다.

```bash
source ~/ros2_practice_ws/house_env_cyclone.bash
python3 ~/ros2_practice_ws/wheel_geometry_audit.py
```

파일만 읽으며 로봇을 움직이거나 설정을 바꾸지 않습니다. 출력에는 형상 거리, 설정 거리, 차이, 좌우 반경, odometry_source가 포함됩니다. 결과는 `~/ros2_practice_ws/wheel_geometry_report.json`에 저장됩니다.

기본으로 설치 패키지의 Waffle Pi SDF를 읽습니다. 다른 파일로 스폰했다면 다음처럼 그 파일을 직접 지정합니다.

```bash
python3 ~/ros2_practice_ws/wheel_geometry_audit.py --sdf /실제로/스폰한/model.sdf
```

설치 SDF가 현재 스폰된 모델과 동일하다는 보장은 없습니다. 그 확인 전에는 결과를 구동기에 적용하지 않습니다. 상대 프레임을 사용한 복잡한 SDF나 원통이 아닌 바퀴는 추측해 계산하지 않고 중단합니다.

## 2. 유효 반경·거리 측정

WORLD 기준 오도메트리를 사용할 때만 `/joint_states`와 `/odom`을 함께 기록해 후보 치수를 계산합니다. 센서 수신이 안정적이고 충돌 없이 움직일 수 있는 실내 빈 공간에서 진행합니다. 수신 공백 문제가 계속되면 먼저 그 문제를 확인해야 합니다.

```bash
python3 ~/ros2_practice_ws/wheel_geometry_audit.py --observe 60
```

이 도구는 스스로 주행 명령을 보내지 않습니다. 60초 동안 다른 단일 조종기로 직진과 좌우 회전이 포함된 움직임을 수행해야 합니다. 정지 상태나 한 가지 곡률의 원운동만 있으면 유효 치수를 구분할 수 없어 추정하지 않습니다. 여러 조종기를 동시에 실행하지 마세요. 특히 키보드 조종을 사용할 때는 기존 벽 추종기와 Nav2를 먼저 종료해야 합니다.

사용하는 식은 다음과 같습니다.

```text
Δs = (rL × ΔφL + rR × ΔφR) / 2
Δθ = (rR × ΔφR - rL × ΔφL) / B
```

`rL`, `rR`은 좌우 유효 반경이고 `B`는 유효 중심 거리입니다. 여러 구간으로 최소제곱 추정합니다. 바퀴 회전각의 단위는 rad입니다. WORLD 위치와 바퀴 센서 시각을 보간해 비교하며, 센서 공백·시각 역행·부족한 움직임은 거절합니다. 보고서에는 거리·회전 잔차도 함께 저장하며 **자동 적용하지 않습니다.**

추정은 기본 모델의 오도메트리 기준과 바퀴축 중심이 같다는 조건을 사용합니다. 커스텀 모델, 축 방향 변경, 다른 오도메트리 기준점은 별도 변환 확인이 필요합니다. 타이어 미끄러짐이나 접촉 문제도 유효 치수 추정에 섞일 수 있으므로 반복 측정의 일관성을 봐야 합니다.

ENCODER 오도메트리와 같은 엔코더를 비교해서는 독립적인 보정이 되지 않습니다. 향후 실물에서는 외부 거리·회전각 측정이 필요하며, 시뮬레이션 추정치를 그대로 적용하지 않습니다.

## 검증

순수 Python 검사 49개와 문법 검사를 통과했습니다. 새 검사에는 형상 중심 거리, WORLD 기본값과 ENCODER 명시값, 서로 다른 좌우 반경 및 축간거리 복원, 부족한 움직임 거절, 시각 보간, 오차가 큰 접촉 측정의 선별이 포함됩니다. Ubuntu의 실제 보정 설정 적용은 아직 수행하지 않았습니다.

## 접촉이 있었던 60초 측정 결과

사용자가 측정 중 접촉 또는 헛돎이 있었다고 확인했습니다. 추정 반경은 좌 0.03013m, 우 0.03113m, 유효 축간거리는 0.20591m이고, 거리 잔차 약 9.49mm, 회전 잔차 약 4.29도였습니다. 이 측정은 정상 주행의 일정한 치수 오차만을 나타내지 않으므로 보정값으로 적용하지 않습니다. 추정 유효 거리는 실물 축간거리를 직접 측정한 값이 아닙니다.

도구는 이제 원본 시각·오도메트리·바퀴 회전 자료를 `wheel_geometry_samples_<번호>.json`에 보존하고, 직진·좌회전·우회전 구간 수와 잔차를 출력합니다. 잔차 5mm 또는 2도 초과, 형상 대비 치수 10% 초과 차이 등을 시험용 선별 기준으로 표시합니다. 이 숫자는 공식 허용 오차가 아니며, 통과해도 보정 자동 적용을 허용하지 않습니다. 접촉 없는 반복 측정과 기준 모델 확인이 필요합니다.

다음 측정은 House 안의 좁은 공간 대신 같은 Waffle Pi의 빈 Gazebo 월드에서 진행하는 편이 좋습니다. 기존 주행기·Cartographer·Gazebo를 각각 Ctrl+C로 종료하고 빈 월드를 실행합니다.

```bash
source ~/ros2_practice_ws/house_env_cyclone.bash
ros2 launch turtlebot3_gazebo empty_world.launch.py
```

Nav2와 Cartographer는 켜지 않습니다. 다른 터미널에서 키보드 조종기를 준비하고, 또 다른 터미널에서 수정한 도구로 60초 관측을 실행합니다. 직진으로 총 0.5m 이상 이동하고 좌우 제자리 회전을 모두 포함합니다. 이 프로그램 자체는 주행시키지 않습니다. 센서 수신이나 측정이 실패하면 이유를 확인하며 결과를 억지로 적용하지 않습니다.
